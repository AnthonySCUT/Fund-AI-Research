## 3. Pod2 要做什么：从输入到验收

### 3.1 输入与输出

输入：基金代码与主数据、Pod1 的日期/价格口径和质量报告、公告标题/发布日期/发布方/原文入口。输出：按基金归属的事件记录，以及包含事实、积极证据、风险信号、待验证问题、研究结论和来源的研究卡片。

工程流程：抓取公开披露 → 识别文档类型 → 映射基金代码 → 向模型提供结构化指标与事件 → 校验输出 → Grok 失败尝试 DeepSeek → 仍失败生成明确标记的规则卡片 → 缓存与快照 → 页面展示 → 人工检查原文和结论。

现有提示词输入主要是公告元数据与指标，不包含完整公告正文。因此能证明的是“有该公告及入口”，不能自动证明原文中的经营细节，更不能把 AI 归因当成已经验证的因果关系。事实、模型推测与待验证项必须分开讲。

### 3.2 六类具体任务

1. 公告证据：选取报告、分红、其他公告等样例，核对代码、基金名称、日期、文档类型、发布方、链接是否指向匹配的文件；公告索引和原文分开记录。对于同指数不同发行人的 ETF，不能只按指数名称匹配。
2. 卡片质量：逐项核对事实、风险和结论是否受输入支持。没有原文支持的内容改为待核验；规则卡片不包装成 AI 已成功分析。
3. AI 接口：保持 Grok 优先、DeepSeek 备用、规则基线兜底。校验返回结构和基金代码，单只失败不妨碍其他有效结果使用。
4. 缓存与增量：默认 1800 秒缓存；仅事实发生变化的基金重新分析；验证公告变动、指标变动、质量变动会触发更新，输入顺序变化不应无故重复计费。
5. 定时任务：检查 Actions 的依赖安装、Secrets 配置、任务日志与快照时间。代码有定时配置并不等于定时任务已成功运行。
6. 汇报证据：保存样例编号、输入输出、代码提交、测试日志、原文复核记录和提示词修改前后对照；同一示例贯穿三 Pod 演示。

## 4. 本次完善与实际完成记录

### 4.1 已修复内容

A. 模型输出校验。过去解析 JSON 后直接接收 status、facts 等字段；例如 facts 返回字符串或状态返回“买入”，仍可能被视作有效卡片；单卡响应为 null 等异常形状也可能中断流程。现在统一校验状态枚举、事实等字段的字符串列表类型、非空事实与结论，以及可选目标字段类型。批量输出只接受本次请求的基金代码，重复代码丢弃并回退，坏卡片由下一供应商或规则基线接管。结构校验不等于内容真实性验证，人工证据复核仍保留。

B. 后台增量指纹。内存 QualityReport 的 warnings 是列表且无 status 字段；快照经 quality_frame 保存后，warnings 是以分号连接的字符串，另有 status。直接对两种形式做哈希会误判为变化。现统一警告表示、忽略派生展示状态，使相同事实具有同一指纹；真实警告变化仍使指纹变化，避免无变化时重复调用模型。

| 来源展示 | 规则、Grok、DeepSeek 来源与实际生成路径一致 | 代码和离线回退已核对；线上待验 |
| 供应商回退 | 模型失败/异常内容后可降级，页面不被单个坏卡片中断 | 离线回归通过；真实 API 待验 |
| 增量与缓存 | 相同事实不变、警告等事实变化可触发更新；页面缓存行为可演示 | 指纹离线通过；页面待验 |
| 跨 Pod 闭环 | 同一 ETF 可追溯到指标、公告、卡片及费用候选 | 待集成 |

建议卡片评审表列：样例ID、基金代码、公告类型/日期、入口URL、原文是否打开、逐条事实及出处、风险是否推断、待验证是否明确、来源标签、问题严重度、复核人、复核日期、整改提交。评分维度各 0–2 分：事实一致、出处可追溯、事实/推断分离、风险合理、来源透明；建议 ≥8/10 且“错配基金/捏造内容”为 0 才通过。本评分是建议标准，不是已有评审结果。

### 7.3 成本管理

人力基线：12 人时，杨/彭各 6。若课程需要货币化，填入统一的人时费率 r，计划人力成本为 12r；没有提供费率，不能编造工资成本。实际记录每包耗时，偏差超过计划 20% 时复核原因和剩余范围；这是建议阈值。

API 成本：按供应商实际账单记录输入/输出 token、模型、调用次数、失败和回退次数；费用 = Σ(输入token×输入单价 + 输出token×输出单价)，使用相同计价单位，并加托管/数据服务费用。本次没有调用真实模型，付费模型调用数为 0；不能据此声称部署后的费用为 0。

控费措施：30 分钟缓存、逐基金事实更新、批量请求、超时和规则回退；本次指纹修复直接服务于“事实未变不重复分析”。验收时记录首次调用、缓存复用、单只变化更新的次数差异，不在没有账单时报告节省金额。模型版本或提示词更新后快照如何失效仍需后续完善。
